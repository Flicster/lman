# BRD: получение информации об установленных языках программирования

## 1. Назначение

`lman` — локальная CLI-утилита для получения единого представления об установленных языках программирования, их версиях, расположении и конфигурациях.

Текущий этап является полностью read-only. Установка, обновление, удаление и переключение версий вынесены в `roadmap.md`.

## 2. Проблема

На машине разработчика могут одновременно находиться:

- несколько языков программирования;
- несколько версий одного языка;
- системные и пользовательские установки;
- установки сторонних менеджеров версий;
- разные системные и пользовательские конфигурации;
- конфликтующие пути в `PATH`.

Пользователю сложно быстро определить, что установлено, где находится каждая версия и какая установка фактически используется.

## 3. Цели

- Показать все поддерживаемые языки, обнаруженные на локальной машине.
- Показать все найденные установки выбранного языка.
- Определить версию и путь каждой установки.
- Показать фактически активную установку.
- Показать расположение известных конфигурационных файлов языка.
- Предоставить безопасный, предсказуемый и пригодный для автоматизации CLI.

## 4. Границы текущего этапа

### Входит в scope

- локальное сканирование Linux и macOS;
- обнаружение языков и установок;
- определение версий и путей;
- определение активной установки;
- поиск путей конфигураций;
- человекочитаемый CLI-вывод;
- управляемые ошибки и стабильные коды завершения.

### Не входит в scope

- установка новых языков или версий;
- обновление и удаление установок;
- изменение активной версии;
- изменение `PATH`, символьных ссылок и shell-конфигурации;
- чтение или изменение содержимого конфигурационных файлов;
- загрузка данных из сети;
- управление зависимостями проектов;
- проектное закрепление версии;
- исправление найденных конфликтов.

## 5. Пользователи

### Разработчик

Проверяет установленные языки, версии, расположение исполняемых файлов, активную установку и конфигурации.

### Инженер поддержки

Использует вывод утилиты для диагностики локального окружения без риска его изменения.

### Инженер автоматизации

Использует коды завершения и разделение `stdout`/`stderr` в локальных скриптах.

## 6. Термины

- **Язык** — поддерживаемый `lman` язык программирования, runtime или SDK.
- **Установка** — конкретная версия языка, доступная по определенному пути.
- **Активная установка** — установка, в которую разрешается стандартный вызов инструмента языка в текущем окружении.
- **Конфигурация** — известный системный или пользовательский конфигурационный файл языка.
- **Стратегия обнаружения** — правила поиска и определения версии для конкретного языка и ОС.

## 7. Бизнес-процессы

### BP-01. Сканирование установленных языков

Система должна:

- сканировать локальную машину и обнаруживать поддерживаемые языки (`BR-SCAN-01`);
- находить все доступные установки каждого языка (`BR-SCAN-02`);
- определять версию и путь установки (`BR-SCAN-03`);
- учитывать `PATH`, стандартные системные и известные пользовательские каталоги (`BR-SCAN-04`);
- продолжать сканирование при ошибке отдельного каталога или установки (`BR-SCAN-05`);
- не изменять файлы, конфигурации и окружение (`BR-SCAN-06`).

### BP-02. Просмотр списка языков

По команде `lman list` система должна:

- выводить обнаруженные языки (`BR-LIST-01`);
- включать язык только при наличии установки (`BR-LIST-02`);
- выводить каждый язык один раз (`BR-LIST-03`);
- использовать стабильный порядок (`BR-LIST-04`);
- не изменять состояние системы (`BR-LIST-05`).

### BP-03. Просмотр установок языка

По команде `lman <language>` система должна:

- выводить все установки выбранного языка (`BR-INFO-01`);
- показывать версию и путь каждой установки (`BR-INFO-02`);
- явно отмечать активную установку (`BR-INFO-03`);
- определять активность по фактическому окружению (`BR-INFO-04`);
- различать неподдерживаемый язык и отсутствие установок (`BR-INFO-05`).

### BP-04. Просмотр конфигураций

По команде `lman <language> cfg` система должна:

- выводить пути известных конфигураций (`BR-CFG-01`);
- искать системные и пользовательские конфигурации (`BR-CFG-02`);
- включать только существующие пути (`BR-CFG-03`);
- не читать и не изменять содержимое файлов (`BR-CFG-04`);
- однозначно сообщать об отсутствии конфигураций (`BR-CFG-05`).

### BP-05. Общие требования к CLI

Все команды текущего этапа должны соответствовать нефункциональным требованиям из раздела 11.

## 8. Основные пользовательские сценарии

### Получение списка языков

1. Пользователь запускает `lman list`.
2. Система сканирует известные локальные источники.
3. Установки группируются по языку.
4. Уникальный список выводится в стабильном порядке.

Пример:

```text
$ lman list
go
java
python
```

### Получение информации о языке

1. Пользователь запускает `lman <language>`.
2. Система находит все установки языка.
3. Система получает версию каждого исполняемого файла.
4. Система определяет активную установку по текущему окружению.
5. Система выводит версию, путь и признак активности.

Пример:

```text
$ lman go
go1.26.5 /usr/local/go/bin/go active
go1.24.0 /usr/go/bin/go
```

### Получение путей конфигураций

1. Пользователь запускает `lman <language> cfg`.
2. Система проверяет известные пути конфигураций.
3. Система выводит существующие пути, не читая содержимое файлов.

Пример:

```text
$ lman go cfg
/home/user/.config/go/env
```

## 9. Правила обнаружения

- Для каждого языка должна существовать отдельная стратегия обнаружения.
- Стратегия определяет имена исполняемых файлов, каталоги поиска, способ получения версии и известные конфигурации.
- `PATH` проверяется с сохранением его приоритета.
- Стандартные и пользовательские каталоги проверяются дополнительно.
- Одинаковый физический исполняемый файл, найденный по нескольким ссылкам, не должен ошибочно считаться несколькими установками.
- Символьный путь и разрешенный физический путь могут выводиться отдельно, если это помогает объяснить активность.
- Если версию определить невозможно, установка показывается с диагностическим статусом, а не отбрасывается молча.
- Если активную установку определить однозначно нельзя, система показывает конфликт и не назначает активную версию произвольно.

## 10. Правила вывода и ошибок

- `stdout` содержит результат команды.
- `stderr` содержит предупреждения и ошибки.
- Успешный пустой результат должен отличаться от ошибки выполнения.
- Неподдерживаемый язык возвращает ненулевой код завершения.
- Ошибка отдельного каталога не блокирует вывод остальных результатов.
- Порядок языков, установок и конфигураций должен быть стабильным.
- Цвет и оформление отключаются, если вывод направлен не в TTY.
- Точные коды завершения должны быть зафиксированы в CLI-контракте до релиза.

## 11. Нефункциональные требования

### `NFR-01` Поддерживаемые платформы

Утилита должна работать в Linux и macOS.

### `NFR-02` Только чтение

Ни одна команда текущего этапа не должна изменять файловую систему, конфигурации или окружение.

### `NFR-03` Управляемые ошибки

Ожидаемые ошибки должны приводить к понятной диагностике и документированному ненулевому коду завершения без аварийного завершения процесса.

### `NFR-04` Предсказуемый вывод

Результаты должны иметь стабильный порядок и не смешиваться с диагностикой.

### `NFR-05` Частичная доступность

Ошибка отдельного источника не должна блокировать достоверные результаты из остальных источников.

### `NFR-06` Конфиденциальность

Утилита не должна читать содержимое найденных конфигураций или отправлять локальные данные за пределы машины.

### `NFR-07` Работа без сети

Все функции текущего этапа должны работать без сетевого доступа.

### `NFR-08` Автоматизация

Результат и диагностика должны разделяться между `stdout` и `stderr`; поведение без TTY должно быть неинтерактивным.

### `NFR-09` Производительность

Сканирование должно завершаться за приемлемое для интерактивной CLI время. Численные SLO определяются после утверждения языков и каталогов поиска.

## 12. Критерии приемки MVP

MVP считается принятым, если:

1. Утилита запускается в утвержденных версиях Linux и macOS.
2. `lman list` выводит уникальный список обнаруженных поддерживаемых языков.
3. `lman <language>` выводит все тестовые установки, версии и пути.
4. Активная установка совпадает с фактическим разрешением команды в тестовом окружении.
5. `lman <language> cfg` выводит существующие известные пути конфигураций.
6. Ни один сценарий не изменяет проверяемую файловую систему и окружение.
7. Недоступный тестовый каталог не блокирует обнаружение остальных установок.
8. Неподдерживаемый язык, отсутствие установок и внутренняя ошибка различаются.
9. Вывод повторного запуска при неизменном окружении стабилен.
10. Все основные сценарии работают без сети.

## 13. Метрики успеха

До пилота должны быть установлены численные целевые значения. Предлагаемые метрики:

- доля корректно обнаруженных установок в тестовой матрице;
- доля корректно определенных версий;
- доля корректно определенных активных установок;
- доля известных конфигураций, найденных в тестовой матрице;
- медианное и максимальное время полного сканирования;
- количество ложных дублей и пропущенных установок.

## 14. Риски

- Формат вывода версии различается между языками и версиями.
- Вызов исполняемого файла для получения версии может зависнуть или иметь побочные эффекты.
- Сторонние менеджеры версий используют shims и динамическое разрешение путей.
- Символьные ссылки могут создавать дубли и циклы.
- Ограниченные права могут скрывать часть установок.
- Полный поиск по файловой системе неприемлем по производительности, поэтому требуется ограниченный перечень каталогов.
- Понятие конфигурации неодинаково для разных языков и может зависеть от переменных окружения.
